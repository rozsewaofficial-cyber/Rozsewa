## 1. How this fits the codebase

Three facts about RozSewa shape every decision below. Getting them wrong is where a straightforward feature turns into a week of debugging.

### 1.1 A Sewak is a Provider document

There is no separate Sewak collection. `Provider.providerCategory` is `'partner' | 'sewak'`, and Sewaks register through `POST /api/provider/register-sewak`.

**Consequence:** every notification, auth guard, and query in this plan uses `userRole: 'provider'` and the existing `protect` middleware. No new auth layer is needed.

### 1.2 "Service" means two different things

The system carries two parallel service concepts. The Skill Session flag has to live on the one the Sewak actually touches.

| Concept | Shape | Who writes it | Where the Sewak meets it |
|---|---|---|---|
| **Catalog service** | `Category.services[]` (embedded `subServiceSchema`) | Admin — Services Catalog, "Base Services" tab | Registration step 4, "Add Services" |
| **Listing service** | `Service` collection | Provider/Sewak — *Provider Services* page | Their own live service list |

`createAdminService` and `updateAdminService` in `backend/controllers/subcategoryController.js` already keep the two in sync. This plan **extends that existing sync** rather than inventing a third source of truth.

### 1.3 The Sewak stores service *names*, not IDs

`Provider.subServices` is `[String]`. Registration step 4 pushes `s.name`, never `s._id`.

**Consequence:** any join between a Sewak and a service must go through a normalized name key. See [D2](#d2--what-identifies-the-service-on-a-session-record).

## 2. Design decisions

Ten calls that need making before any code is written. Each names the tradeoff so it can be overruled deliberately rather than discovered later.

### D1 — Where does "Skill Session Required" live?

**Decision:** On `subServiceSchema` in `Category.js` as canonical, mirrored onto `Service.js`, with the existing admin sync carrying the fields across.

Four fields:

| Field | Type | Default |
|---|---|---|
| `skillSessionRequired` | Boolean | `false` |
| `sessionDurationMinutes` | Number | `60` |
| `sessionMode` | `'online' \| 'offline'` | `'offline'` |
| `skillSessionActive` | Boolean | `true` |

**Why:** The brief's "Active / Inactive" on the Services block means *the requirement* is active — not the service. Naming it `skillSessionActive` avoids collision with the existing `Service.visible` and `Category.isActive`. Turning it off suspends the gate without losing the config.

### D2 — What identifies "the service" on a session record?

**Decision:** Store all three — `categoryId` (ref), `serviceName` (display), and `serviceKey` (lowercase-trimmed name, indexed). Every certification lookup joins on `(sewakId, categoryId, serviceKey)`.

**Why:** Because `Provider.subServices` holds names, an ID-only join silently returns nothing. The normalized key survives casing drift and stray whitespace from the admin catalog. Keep `serviceId` as an optional reference for reporting, never as the join key.

### D3 — How does city matching work?

**Decision:** `TrainingCenter.cities` is `[String]` of Zone names, with a parallel `citiesNormalized: [String]` maintained by a schema setter. Match on the normalized array. For `mode === 'online'`, skip the city filter entirely.

**Why:** `Provider.city` is free text from the Nominatim reverse geocode at registration ("Varanasi", sometimes with trailing spaces). `Zone.name` is the curated admin list. Normalizing both sides at write time keeps the lookup a plain indexed query instead of a regex scan.

### D4 — How are availability and capacity modelled?

**Decision:** Both Center and Trainer carry `availability: [{ day, startTime, endTime }]` and a numeric `capacity`. Slots are generated by chopping the overlap of the two windows into `sessionDurationMinutes` chunks.

- `Trainer.capacity` — seats per slot
- `TrainingCenter.capacity` — total seats per day, a second ceiling so one center can't be oversold across its trainers

Times are stored as 24-hour `"HH:mm"` strings and days as `'mon'…'sun'`, matching the existing `Provider.availability` shape.

### D5 — What happens when nothing is available?

**Decision:** The session is created with status `pending` and a retry cron re-attempts allocation every 30 minutes. Admin sees every pending session at the top of the console and can assign one by hand.

**Why:** Rejecting the booking pushes an internal capacity problem onto the Sewak, who has no way to act on it. A pending session is a queue the business can staff against; a rejection is a dead end. The allocator searches the preferred date first, then the following 14 days, before giving up to pending.

### D6 — Is a re-session a new record or a status change?

**Decision:** A new `SkillSession` document with `isReSession: true`, `parentSessionId`, and an incrementing `reSessionRound`. The original keeps its `no_show` or `completed` status.

**Why:** The brief asks for "Total Sessions", "No Show", and "Re-Session" as separate report figures. Mutating the original record in place makes those numbers unrecoverable — a Sewak who no-showed twice would read as one clean completion. Separate rows keep the history honest and make the report a simple aggregation.

### D7 — How is "Service Ready for Activation" enforced?

**Decision:** Denormalize completions onto `Provider.skillCertifications[]`, written at exactly one place — the `markAttendance` controller.

**Why:** A single writer means the array can't drift. Read paths (`getMyServices`, the services list UI, the activation check) then need no join at all. Querying `SkillSession` on every service render adds a lookup to a hot path for no correctness gain.

### D8 — Does an ungated service get blocked at creation?

**Decision:** No. It is created with `visible: false` and `pendingSkillSession: true`, and the UI shows "Skill Session required" with a Book Session button. Completion flips it visible automatically.

**Why:** Hard-rejecting the save loses whatever the Sewak typed — pricing, description, photos — and gives them nothing to do about it. Saving it in a held state turns the gate into a single clear next step, which is what "Service Ready for Activation" describes.

### D9 — Who marks attendance?

**Decision:** Admin only, for v1. Trainer login is out of scope.

**Why:** Trainers exist as records with a name and mobile number — there is no trainer auth, no trainer session, no trainer app surface anywhere in the codebase. Building one is a feature in its own right. The admin console marks `completed` or `no_show`, and the record keeps `attendanceMarkedBy` so trainer self-service can be layered on later without a migration.

### D10 — How is the last-seat race handled?

**Decision:** Optimistic — count, insert, then re-verify and reallocate if the slot went over.

**Why:** Two Sewaks can hit the same final seat between the count and the insert. At RozSewa's booking volume this is rare and self-healing: the post-insert re-count catches the loser and re-runs the allocator, which lands them in the next slot. The rigorous fix is a MongoDB transaction across the count and the insert — worth doing if session volume ever justifies it, and noted here so the tradeoff is a choice rather than an oversight.

## 4. Allocation engine

One pure function in `backend/utils/skillSessionAllocator.js`, called from the booking controller and again from the retry cron. Keeping it free of Express request state is what makes it testable and reusable across both callers.

```
allocate({ sewak, categoryId, mode, durationMinutes,
           preferredDate, preferredTimeOfDay })

1  centerQuery = { isActive: true, categories: categoryId }
   if (mode === 'offline')
     centerQuery.citiesNormalized = normalize(sewak.city)

2  centers = TrainingCenter.find(centerQuery)
   sort by sessions-already-booked-today ASC        // load balance

3  for each center:
     trainers = Trainer.find({ isActive: true,
                               trainingCenter: center._id,
                               categories: categoryId })
     sort by sessions-already-booked ASC

     for each trainer:
       windows = intersect(center.availability, trainer.availability)

       for date from preferredDate to preferredDate + 14 days:
         if centerDayCount(center, date) >= center.capacity: continue

         slots = chop(windows[weekday(date)], durationMinutes)
         order slots: preferredTimeOfDay first, then the rest

         for each slot:
           if bookedCount(trainer, date, slot) < trainer.capacity
             return { centerId, trainerId, date, slot }

4  return null        // caller writes status: 'pending'
```

### 4.1 Time-of-day bands

| Band | Range |
|---|---|
| `morning` | `< 12:00` |
| `afternoon` | `12:00 – 16:59` |
| `evening` | `>= 17:00` |

**The preference orders the slot list; it never filters it.** A Sewak who asks for evening and finds none still gets scheduled rather than dropped to pending — which is the whole point of the system choosing for them.

### 4.2 Load balancing

Sorting centers and trainers by current booking count spreads sessions instead of filling the first matching trainer to capacity and leaving the rest idle. Both sorts are a single aggregation each, run once per allocation.

## 7. Known traps

Five places where this codebase will **silently discard correct-looking work**. Each was found by reading the existing implementation, and each costs hours if hit blind.

### Trap 1 — `updateCategory` rebuilds services from a field whitelist

**Location:** `backend/controllers/adminController.js`, line 543

It does not merge — it reconstructs every entry from exactly `{ _id, name, basePrice, description }`:

```js
category.services = req.body.services.map(s => {
    const existing = category.services.find(/* ... */);
    return {
        _id: existing?._id || s._id || new mongoose.Types.ObjectId(),
        name: s.name,
        basePrice: Number(s.basePrice) || 0,
        description: s.description || existing?.description || ""
        // image is ALREADY being dropped here today
    };
});
```

Adding fields to the schema is **not enough**. Any Skill Session config will be wiped the next time an admin edits base services, and nothing will error.

**Fix in Phase 1.** Extend that map, and take `image` with it while you're there.

### Trap 2 — The Notification type enum rejects unknown values

**Location:** `backend/models/Notification.js`, line 8

```js
type: { type: String, enum: ['booking', 'payment', 'system', 'offer',
        'scrap', 'bazaar', 'lead', 'test', 'login'], default: 'system' },
```

`'skill_session'` is not among them, so `Notification.create` throws a validation error — which `notifyUser` **catches and logs as `inAppStatus: 'fail'` while returning normally**. Push still delivers, so the bug looks like *"notifications work but the bell is empty."*

**Fix in Phase 1.** Add the value to the enum.

### Trap 3 — Email and SMS only fire for booking and payment

**Location:** `backend/config/notificationService.js`, line 403

```js
if (userRole === 'provider' && (type === 'booking' || type === 'payment') && bookingId) {
```

Skill sessions satisfy neither condition, so they reach **in-app, socket, and FCM only**.

That is the right default — five session events over SMS is noise. But know it's a deliberate consequence, not a bug. If session SMS is wanted later, it needs a branch in `mapEventDetails` plus a widened condition, not a type rename.

### Trap 4 — Sewak services join by name, not by id

`Provider.subServices` is `[String]`. Registration step 4 pushes `s.name`.

Any eligibility check written against `_id` **returns an empty list on real data while passing every hand-seeded test.**

**Always join through `serviceKey`** — see [D2](#d2--what-identifies-the-service-on-a-session-record).

### Trap 5 — `Provider.city` is unvalidated geocoder output

It is written straight from the Nominatim reverse lookup during registration and can be a city, a town, a village, or a county — with casing and whitespace nobody normalized:

```js
city: addr.city || addr.town || addr.village || addr.county || ""
```

It will not reliably equal a `Zone.name`.

Match on `citiesNormalized` ([D3](#d3--how-does-city-matching-work)), and let the pending queue absorb the mismatches instead of failing the booking.

## 8. Out of scope for v1

Named here so they read as decisions rather than omissions. Each has a clean seam to be added later without a migration.

| Not building | Why · seam for later |
|---|---|
| **Trainer login** | No trainer auth exists anywhere in the codebase. Admin marks attendance ([D9](#d9--who-marks-attendance)); `attendanceMarkedBy` is already stored, so a trainer role slots in cleanly. |
| **Sewak-chosen center or trainer** | Explicitly against the brief. The allocator's seam makes it a UI change if that ever reverses. |
| **Paid sessions** | No wallet, commission, or ledger integration. Sessions are free. |
| **Session content** | No curriculum, materials, or assessment — attendance is the only signal. |
| **Automatic meeting link generation** | Admin pastes a link. No Zoom or Meet API integration. |
| **Certificates** | No PDF or shareable credential on completion. |
